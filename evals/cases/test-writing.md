# Test writing

The input is `test-writing-input.ex`, a GenServer that notifies subscribers and sends email through a behaviour.

## Prompt

```text
Write ExUnit tests for the `Notify.Subscriptions` module at <evals>/test-writing-input.ex. Cover subscribing, publishing to process and email subscribers, listing subscribers, and what happens when a subscribed process exits.

Write the tests to <output>/subscriptions_test.exs. The file must start ExUnit itself, so that `elixir -r <evals>/test-writing-input.ex <output>/subscriptions_test.exs` runs it (Elixir <elixir-version> is installed; no Mix project and no Hex packages are available). Reply with just the file path when done.
```

## What to check

- The test module uses `async: true`, and the mailer double reaches the test process without `Process.register/2` on the test pid or the application environment.
- Each test starts its own server with `start_supervised!/1` and a test-specific `:name`, or no name. A test that asserts a start failure calls `start_supervised/1` and matches the reason; nothing calls `start_link` from a test.
- The mailer is replaced through the `Notify.Mailer` behaviour (a test module that implements it, or a mock built on it), not by redefining `Notify.Mailer` or patching modules at runtime.
- Notifications are awaited with `assert_receive` and `refute_receive`. There is no `Process.sleep/1`.
- The exit test monitors the process and waits for the `:DOWN` message, or calls `:sys.get_state/1`, before asserting that the subscriber is gone. There is no polling of `Process.alive?/1`.
- Assertions use patterns (`assert [^pid] = ...`, `assert_receive {:notification, "news", %{id: 1}}`) or `==` on the whole value, not `elem/2` or `==` on a tuple's parts; a value the test already holds is pinned or compared whole, not bound by a match and compared with `==` afterwards.
- Tests are grouped in `describe` blocks named after the function under test or after a condition the block's tests share; no block joins two functions, and a condition block states a behaviour, not a topic (`"when a subscriber exits"`, not `"exits"`). Test names say what the call did, not only its return value (`returns :ok`).
- Shared setup returns a map that tests match in their heads.
- Only public functions are tested.
- `do:` appears only on a body of one expression with no `fn`, block construct or capture holding a call with its own arguments inside it; a body with several steps, a `case` or a `fn` uses `do ... end`; a one-line `if ..., do: ..., else: ...` has a name or a literal as one of its branches; every `for` is `do ... end`; a function that mixes `do:` and block clauses sets each block clause apart with a blank line; no `do:` body, on a function or an `if`, is wrapped onto a line of its own, except under a head that `mix format` broke after a long guard.
- A pipeline of two or more steps is never on one line: each `|>` starts a new line under the value, and a two-step pipeline may be a nested call instead; no pipeline starts with an argument that only selects a kind or a mode.
- The file passes `mix format --check-formatted` and the tests pass.
- In an `assert` with `==`, the call under test is on the left and the expected value on the right.
- `use`, `import`, `alias` and `require` are grouped in that order right after `@moduledoc`.
- Expected reads: `ex_unit.md` and `processes.md`.
